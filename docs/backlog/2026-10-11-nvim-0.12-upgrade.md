# 2026-10-11 — nvim v0.12.6 upgrade + Telescope repair

## What changed

- **nvim 0.11.5 → v0.12.6** (latest stable, published 2026-10-09). Built from source in
  `~/dev/neovim` at tag `v0.12.6` (commit `779c36969e`); `sudo make install`; installed
  `/usr/local/bin/nvim` sha256 `02819703c5e760f6e5d80cf879e86ba6b62c2f8cd8a5d64d3d3783d2dc2617c6`
  == build output. No brew involved. Binary saved at
  `~/.local/share/nvim/nvim-v0.11.5-backup` (sha `0a9bbfff…`).
- `lua/plugins/pluginsHub.lua:136-143` — telescope spec: dead `init` stub removed; lazy
  `keys` placeholders added for `<leader>ff/fb/fg/fh/U`, `;e` (load telescope on first press,

- `lua/core/keymappings.lua:621` — the Snacks entries `ff/fb/fg` deleted (they were stealing

## Why

Owner request: upgrade nvim without brew (latest stable), update packages via the lazy logic,
and diagnose "telescope keybinding does not work, typing in it is blocked".

Intake found two independent root causes, neither one inside telescope:

1. **Typing blocked** — `avante.nvim/plugin/avante.lua:1-9`: on nvim < 0.12 it echoes an error,
   runs `vim.fn.getchar()` (eats the next keystroke) and `vim.cmd("quit")` (closes the picker
   window). The spec loads avante on `InsertEnter` (`pluginsHub.lua:1181-1183`) — and every
   picker opens in insert mode. Today's earlier `:Lazy update` (13:41) had moved avante to the
   commit that introduced the hard 0.12 gate; the old commit only gated at 0.10. Fixed by the
   nvim upgrade itself.
2. **Keys dead** — commit 891db25 (2026-10-07 startup speed) removed telescope's `event =
   "VimEnter"`; its keymaps (`gi_telescope.lua:34-83`, registered at module load, `:255`) then
   only appeared after telescope loaded, while Snacks (lazy=false) owned `ff/fb/fg/fp` at startup
   and `fh/fy/U`, `;e` were unmapped. Fixed with lazy `keys` placeholders + deleting the Snacks
   collisions.

## Proof

- `nvim --version` → `NVIM v0.12.6`; sha256 matches `~/dev/neovim/build/bin/nvim` exactly.
- `nvim --headless "+messages" +qa 2>&1` → no output, exit 0 — before and after `:Lazy update`.
- Startup maparg (fresh process): `ff` desc `Find Files (telescope)`, `fh` mapped, `fp`
  `Projects` (Snacks), `fv`/`fy` empty, `package.loaded.telescope = nil` (still lazy).
- First press, one fresh process per key: `ff/fb/fg/fh/U` → `filetype=TelescopePrompt`,
  telescope loaded. `;e` loads telescope and opens the picker when diagnostics exist
  (empty-state shows telescope's own "No diagnostics found" notification — not a defect).
- **Typing, real pty (xterm-256color):** press ` ff`, type `lua` →
  `ft=TelescopePrompt line=[  lua] mode=i avante=true`; the picker filtered to
  `lua/core/init.lua`. On 0.11.5 the same flow died (intake A/B: with the version check
  stubbed, typing worked; stubbed off, the prompt stayed empty).
- Avante: `nvim --headless "+Lazy load avante.nvim"` → `avante_loaded=1`, no version banner,
  no quit.
- `:checkhealth lazy` OK; `:checkhealth telescope` (after load) all green incl. fzf-native
  `lib working as expected`; `:checkhealth vim.treesitter` clean (parsers ABI 13-15).
- Startup time (pty, real UIEnter): 148–174 ms across runs — inside the 140–180 ms baseline
  from `2026-10-07-startup-speed.md`.
- No `<nop>` residue after first press; second key in the same session works.
- Working tree after the work: only the expected files; no untracked leftovers.

**Known red item on 0.12.6:** text objects are broken — `vaf`/`vif` raise E5108
(`nvim-treesitter/tsrange.lua:27` via `query.lua:282`; python at runtime
`vim/treesitter.lua:269`). Cause: installed nvim-treesitter is branch `master`, whose README
says 0.12 is not supported; `iter_matches`'s `all` option was removed in 0.12. Highlighting and
the configs module work. Owner decision (2026-10-11): migration to the `main` branch is the
**next task**, not part of this delivery.
